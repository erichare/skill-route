## 1 — Codebase Purpose

SkillRoute is a local-first skill catalog and router for agent builders. It indexes `SKILL.md` bundles into a SQLite catalog and returns ranked skill plans — confidence, evidence snippets, score breakdowns, clarification prompts — to three callers: the `skillroute` CLI, a TypeScript MCP server (`skillroute.route`, `skillroute.search`, `skillroute.inspect_skill`), and the Skill Atlas web UI.

---

## 2 — Layer Map

The codebase is organized into the following layers, outermost first:

| Layer | Responsibility | Key symbol |
|---|---|---|
| Entry surfaces | CLI argparse tree; MCP stdio server; FastAPI UI server | `cli.build_parser()`, `callBridge()` (mcp/src/bridge.ts), `ui_server.create_app()` |
| Routing | Score, rerank, and dedupe candidates; decide clarification | `Router.route()` |
| Reranking | Pluggable post-scoring reorder | `Reranker` (protocol), `default_reranker()` |
| Retrieval backends | Lexical or remote vector search over indexed skills | `RetrievalBackend` (protocol); `LocalTokenBackend`, `AstraDataAPIBackend` |
| Catalog persistence | SQLite storage of skills, excerpts, relationships, backend refs, route traces | `Catalog` |
| Parsing / indexing | Turn a `SKILL.md` bundle into a `SkillRecord` | `parse_skill_bundle()` |

## 3 — Execution Lifecycle

**Representative execution:** `skillroute route "<request>"`

1. **Entry:** `cli.main()` dispatches to `cli.cmd_route()`, which builds a `Catalog` (via `default_catalog_path()`) and resolves the backend with `backend_from_name()`.
2. **Routing:** `Router.route()` gathers repo signals via `collect_repo_context()` and loads all skills with `Catalog.list_skills()`.
3. **Scoring:** `Router._score_candidates()` blends four signals per skill — `lexical_score()` (0.5), `semantic_score()` from `RetrievalBackend.search()` (0.25), `repo_score()` (0.15), `graph_score()` (0.10) — then sorts and dedupes via `dedupe_candidates()`.
4. **Reranking:** `Reranker.rerank()` (default `HeuristicReranker`) reorders and trims to the limit; `Router._needs_clarification()` decides whether to attach `_clarification_questions()`.
5. **Trace recording:** `Catalog.record_route_trace()` persists the request and full `RouteResponse` (on by default via `record_trace=True`).
6. **Response:** a `RouteResponse` returns to the caller; `cli.print_route()` renders it, or `to_jsonable()` serializes it for `--json`, the bridge, and the UI.

The MCP path reaches step 2 by spawning `python -m skillroute bridge route` from `callBridge()` into `cli.cmd_bridge()`; the UI path reaches it via the `route_preview()` endpoint in `ui_server.create_app()`, which calls `route_preview_payload()` with `record_trace=False` so previews never pollute the trace log.

## 4 — Domain Vocabulary

| Term | Definition |
|---|---|
| **Skill bundle** | A directory with a `SKILL.md` plus referenced files; parsed into a `SkillRecord` by `parse_skill_bundle()`. |
| **Catalog** | The local SQLite database (default `.skillroute/catalog.db`) holding skills, excerpts, relationships, backend refs, and traces. Key class: `Catalog`. |
| **Backend / backend ref** | A retrieval provider implementing `RetrievalBackend`; a backend ref (`Catalog.save_backend_ref()`) links a skill to its indexed copy there. |
| **Overlay** | Reviewed-metadata JSON that overrides parsed frontmatter at index time. Loaded by `load_overlays()`, generated by `write_metadata_overlay()`. |
| **Route trace** | A persisted record of one routing call (request + full response). Written by `Catalog.record_route_trace()`, read by `skillroute traces`. |
| **Excerpt** | A high-signal snippet extracted by `extract_excerpts()` and used as ranking evidence. Class: `SkillExcerpt`. |
| **Facet** | Structured metadata dimension (e.g. `language`) inferred by `infer_metadata()`; drives `repo_score()`. |
| **Golden route** | An eval case asserting expected skills/clarification for a request. Run by `run_golden_routes()`. |
| **Bridge** | The JSON stdin/stdout subprocess contract (`cli.cmd_bridge()`) the MCP server calls through `callBridge()`. |

## 5 — Common Change Recipes

### Recipe A — Add a new CLI subcommand

1. Add a subparser in `cli.build_parser()` and bind it with `set_defaults(func=cmd_yourcommand)`.
2. Implement `cmd_yourcommand(args)` in `cli.py`; support `--json` via `print_json()` and `to_jsonable()`.
3. Put reusable logic in its own module (see `dogfood.py`, `metadata.py`) — `cli.py` stays a thin dispatcher.
4. Add tests in `tests/test_cli.py`.

### Recipe B — Add a new retrieval backend

1. Create a class satisfying the `RetrievalBackend` protocol: `upsert_skills()`, `search()`, `status()`, and a `name` attribute.
2. Add its names to `BACKEND_CHOICES` and a resolution branch in `backend_from_name()` — the single registry shared by CLI, bridge, and UI.
3. Add tests in `tests/test_backends.py` (use `AstraDataAPIBackend`'s injectable transport as the pattern).

### Recipe C — Add a new MCP tool

1. Add the operation to `cli.cmd_bridge()` and to the `bridge` subparser choices in `cli.build_parser()`.
2. Add the operation to `BridgeOperation` in `mcp/src/bridge.ts`.
3. Register the tool with `server.registerTool()` in `mcp/src/index.ts`, defining a zod input schema.
4. Run `npm run build && npm run smoke` in `mcp/`.

### Recipe D — Change routing behavior

1. Adjust the signal functions (`lexical_score()`, `semantic_score()`, `repo_score()`, `graph_score()`) or their weights in `Router._score_candidates()`.
2. If adding a signal, extend `ScoreBreakdown` in `models.py` and `reasons_for()`.
3. Verify with `skillroute eval run --fresh --index-root examples/skills --cases examples/evals/golden_routes.json` and `tests/test_routing.py`.

## 7 — Known Gotchas

### Bridge stdout is sacred

**Rule:** code reachable from `cli.cmd_bridge()` must print exactly one JSON object to stdout; diagnostics go to stderr.
**Why:** `callBridge()` parses the child's entire stdout with `JSON.parse` — there is no framing protocol.
**What breaks:** one stray `print()` anywhere in the routing path corrupts every MCP tool response with "bridge returned invalid JSON". `Catalog.index_root()` writes its skip warnings to stderr for exactly this reason.

### `backend_from_name()` is the only backend registry

**Rule:** wire new backends through `BACKEND_CHOICES` and `backend_from_name()` — never instantiate one ad hoc at a call site.
**Why:** the CLI, bridge, and UI server all resolve backends through this one function so they agree on valid names and the `SKILLROUTE_BACKEND` env fallback.
**What breaks:** an ad-hoc backend works in one entry surface and silently falls back to `LocalTokenBackend` (or errors) in the others.

### Dedupe is by content hash, not name

**Rule:** do not change `_dedupe_key()` in `routing.py` to key on skill name or id alone.
**Why:** the same skill indexed under multiple roots (the dogfood flow) shares a `content_hash` and must collapse to one candidate, while genuinely distinct skills that merely share a name must both survive.
**What breaks:** keying on name drops distinct same-named skills from results; keying on id shows duplicate rows for every multi-root skill.
